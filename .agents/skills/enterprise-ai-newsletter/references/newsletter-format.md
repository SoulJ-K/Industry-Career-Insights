# HTML 뉴스레터 작성 형식 · v04

## 1. 뉴스레터 머리말

다음 정보를 먼저 표시한다.

- 제목: `기업용 AI·업무자동화 직무 인사이트 뉴스레터`
- 실행일
- 수집 기간의 시작일과 종료일
- 전체 자료 수
- 국내·해외 실제 건수와 비율
- 출처 유형별 건수
- 기준보다 자료가 부족하거나 사람이 확인해야 할 사항

실행 방식을 표시한다. 기존 검증 자료 재작성 방식이면 사용한 검증 자료 묶음의 상대 링크와 원래 원문 확인일도 표시한다. `인터넷 검색·원문 재확인: 하지 않음` 항목은 뉴스레터에서 제외한다. 검색 미실시 사실은 내부 규칙과 작업일지에 유지한다. 현재 시점에 다시 확인한 최신 뉴스처럼 표현하지 않는다.

## 2. 구성과 배치

총 5개를 `분석 2개 → 가벼운 읽을거리 1개 → 분석 1개 → 가벼운 읽을거리 1개` 순으로 배치한다. 원문 자료 1건을 콘텐츠 1개로 세고 중복 게재하지 않는다.

- 분석 3개: 산업 동향, 기술·제품 동향, 기업의 AI·업무자동화 적용 사례, 기업의 기술개발 사례, 기업 공식 기술 콘텐츠 중 대표 분야를 붙인다.
- 읽을거리 2개: 흥미로운 AI 이야기·실험, 일상 활용이나 작은 실습 제안으로 구성한다. 직무 분석 질문 8개와 4개 영역을 강제하지 않는다.
- 실제 자료 수와 국내외 구성을 표시한다. 7건 기준의 국내 5건·해외 2건 목표는 폐기한다.

## 3. HTML과 제목 계층

최종 뉴스레터는 외부 글꼴·스크립트·이미지 없이 단독으로 열리는 UTF-8 HTML 파일로 작성한다. 스타일은 `<style>` 안에 둔다. `lang="ko"`, 문자 인코딩과 모바일 화면 설정을 포함한다. 검증 자료 묶음은 Markdown으로 보존한다.

- 분야 제목은 h2, 기사 제목은 h3, 분석 영역은 h4, 세부 질문은 굵은 본문으로 구분한다. 최상단 뉴스레터 제목은 h1이다.
- 분야 제목은 기사보다 크게, 기사 제목은 분석 영역보다 크게 표시한다. 모바일에서도 단계 차이를 유지한다.
- 숫자는 기사 순번 `01.`~`05.`에만 사용한다. 분석 영역은 `■ 무슨 일이 있었나`, 세부 질문은 `• 어떤 업무 문제를 해결하려 했는가?` 형식을 쓴다.
- 분야와 분석 영역 위에 충분한 여백을 두고, 소제목을 본문 문단과 붙여 관계를 드러낸다.
- 기사 제목 바로 아래에 옅은 배경과 경계선으로 구분한 핵심 상자를 둔다. `💡 핵심 한 줄` 표시와 요약 문장을 별도 줄로 나누고, 요약 문장 전체를 굵게 표시한다.
- 핵심 상자 뒤에 기업·기관, 발표일, 국내·해외, 출처 유형과 원문 링크를 간결하게 표시한다.
- 360~390px의 좁은 화면에서 가로 넘침 없이 읽히도록 하고, 긴 링크와 제목이 줄바꿈되게 한다. 화면 대비, 키보드 초점 표시와 인쇄 가독성도 유지한다.
- 이번 버전에는 본문 축약, 접힘 영역, 더 읽기 버튼을 추가하지 않는다. 분석의 모든 답을 처음부터 표시한다.

분석의 기본 정보 다음에는 아래 4개 영역을 배치하고, 마지막에 `직무 학습 포인트`를 한두 문장으로 정리한다.

## 4. 분석 기사 3개의 4개 큰 영역과 필수 질문 8개

분석 기사에만 필수 질문 8개의 분석 내용을 그대로 유지하되 제목을 잘게 나열하지 않고 다음 4개 큰 영역 안에 굵은 글씨의 하위 질문으로 배치한다. 정보가 없더라도 질문을 생략하지 않고 `확인되지 않음`이라고 적는다.

### ■ 무슨 일이 있었나

- **어떤 기업에서 무슨 일이 있었는가?**
  기업·기관명, 발표 주체, 적용 또는 발표된 내용을 설명한다.
- **어떤 업무 문제를 해결하려 했는가?**
  기존 방식의 불편, 반복 작업, 운영 문제와 AI·자동화가 필요했던 이유를 설명한다.

### ■ 어떻게 구현했나

- **AI가 어떤 시스템·데이터와 연결됐는가?**
  기사에서 확인 가능한 기존 시스템, 데이터베이스, API, 업무 도구와 AI의 연결 관계를 설명한다.
- **무엇이 자동화됐고 무엇은 사람이 확인하는가?**
  AI가 분석·판단·실행하는 범위와 사람이 검토·승인·예외 처리하는 범위를 구분한다.

### ■ 근거가 있는가

- **실제 성과를 보여주는 근거가 있는가?**
  시간, 비용, 품질, 처리량 등의 수치와 실제 운영 여부를 확인한다. 근거가 없으면 없다고 쓴다.

### ■ 나의 직무와 어떻게 연결되는가

- **AI 솔루션·업무자동화 개발자는 어떤 일을 했는가?**
  업무 분석, 시스템 설계, 데이터·API 연결, 개발, 테스트, 배포, 운영과 협업 중 어떤 역할이 필요한 사례인지 설명한다. 기사에 직접 적혀 있지 않으면 `직무 관점의 해석`이라고 표시한다.
- **나의 기존 경험과 연결되는 역량은 무엇인가?**
  Java 운영개발, 시스템 분석, 장애 대응, 데이터베이스·API 연결과 운영 부서 협업 경험 중 연결되는 지점을 설명한다.
- **더 공부하거나 직접 만들어볼 것은 무엇인가?**
  사례를 이해하기 위해 더 공부할 개념과 포트폴리오로 시험해볼 수 있는 작은 실습 아이디어를 제안한다.

## 5. 가벼운 읽을거리의 작성 방식

- 약 400~700자 안팎의 짧은 이야기로 쓰되, 필요한 출처와 사실의 한계는 생략하지 않는다.
- 호기심이 생기는 질문으로 시작하고 일상적인 상황이나 비유로 풀어낸 뒤 기억할 한 줄로 마무리한다. 참고 뉴스레터의 문장이나 독특한 표현을 복제하지 않는다.
- 비유·가정은 그 성격이 드러나게 쓴다. 실제 사용자 반응·실험 결과·사용 후기를 만들어내지 않는다. 제안하는 작은 실습은 `직접 해보기 제안`으로 표시하고 이미 실행했다고 쓰지 않는다.
- 검증 자료 재작성에서는 기존 원문의 사실을 이야기로 풀어쓸 수 있다. 새로운 연구나 활용법의 사실이 필요하면 새 자료 수집으로 전환해야 한다.
- 출처·발표일·원문 링크와 핵심 한 줄은 분석 기사와 동일하게 제공한다. 직무 연결은 필요한 경우 한 줄로 충분하다.

## 6. 가독성 작성 원칙

- 친근하지만 과장되지 않은 한국어로 작성한다.
- 기술 설명만 나열하지 않고 `업무 문제 → 구현 방식 → 결과 → 직무 의미` 순서로 연결한다.
- 전문용어는 처음 등장할 때 바로 쉬운 말로 풀이한다.
- 한 문단은 2~4문장을 기본으로 하고, 질문 하나에는 원칙적으로 1~2개의 짧은 문단이나 글머리표로 답한다.
- 같은 기업 정보나 성과 수치를 여러 영역에서 반복하지 않는다.
- 해외 자료도 자연스러운 한국어로 설명하되 제품명, 기술명과 고유명사의 의미를 바꾸지 않는다.
- `핵심 한 줄`에는 세부 수치를 몰아넣지 말고 사건과 직무 의미를 한 문장으로 연결한다.

## 7. 사실과 해석 표시

읽는 흐름을 해치지 않는 범위에서 필요한 곳에만 다음 표시를 사용한다.

- **확인된 사실:** 원문이나 검증 자료에서 직접 확인할 수 있는 내용과 수치는 자연스럽게 서술한다.
- **직무 관점의 해석:** 원문에 직접 나오지 않은 개발자 역할이나 활용 가능성을 분석할 때 표시한다.
- **확인되지 않음:** 신뢰할 수 있는 근거로 확인하지 못한 질문에만 표시한다.

사실과 해석을 한 문장에 섞지 않는다. 기업이 발표한 성과는 `기업 공식 발표 기준`이라고 출처의 성격을 밝힌다. 모든 문장에 표시를 반복하지 않는다.

## 8. 전체 종합

자료 5건 뒤에 분석 3건을 중심으로 다음 내용을 작성한다.

### 이번 호에서 반복해서 나타난 업무 문제

### 자주 사용된 시스템·데이터 연결 방식

### 사람의 검토와 승인이 필요한 지점

### AI 솔루션·업무자동화 개발자에게 중요하게 나타난 역량

### 다음 학습 또는 포트폴리오 실습 제안

각 종합 내용이 어느 자료에서 나온 것인지 번호나 원문 링크로 연결한다.

## 9. 마지막 점검표

- [ ] 모든 자료가 최근 3개월 범위에 있다.
- [ ] 분석 3개 + 읽을거리 2개, 총 5개이며 실제 국내외 건수와 비율을 표시했다.
- [ ] 모든 자료에 제목, 발표일, 출처명과 확인한 원문 링크가 있다.
- [ ] 기업 공식 자료와 독립 언론 보도를 구분했다.
- [ ] 채용, 광고, 출처 불명, 원문 미확인과 중복 자료를 제외했다.
- [ ] 각 자료에 핵심 한 줄과 간결한 기본 정보가 있다.
- [ ] 분석 3개는 각각 4개 영역·질문 8개의 답을 모두 표시했고, 읽을거리 2개는 별도 이야기 형식이다.
- [ ] 확인된 사실, 직무 관점의 해석과 확인되지 않은 내용을 구분했다.
- [ ] 직무 역할을 근거 없이 사실로 단정하지 않았다.
- [ ] 해외 자료도 한국어로 이해하기 쉽게 요약했다.
- [ ] 전문용어를 처음 나올 때 풀어 썼고 같은 정보를 불필요하게 반복하지 않았다.
- [ ] 기존 검증 자료 재작성에서는 인터넷이나 원문을 다시 열지 않고 검증 자료 밖의 사실을 추가하지 않았다.
- [ ] 기존 결과물을 덮어쓰지 않고 새 파일로 저장했다.
- [ ] 최종 파일이 단독으로 열리는 HTML이며 기존 Markdown 결과와 검증 자료를 보존했다.
- [ ] 핵심 한 줄의 전체 문장이 강조되고 제목의 기호·크기·여백이 단계별로 구분된다.
- [ ] 재작성 뉴스레터에 검색 미실시 표시 항목이 없고 입력 자료 링크·원래 기간·확인일은 있다.
- [ ] 본문 축약과 더 읽기 기능을 추가하지 않았다.
- [ ] 자동 검사와 브라우저 화면 검사를 구분해 보고했다. 화면을 확인하지 못했다면 그 한계를 밝혔다.
